第 9 章 检索增强生成 —— 课程实践作业
云南大学软件学院《大规模语言模型：从理论到实践》 对应课件：9.1 基础 → 9.2 模块化架构 → 9.3 设计模式 → 9.4 训练与优化 → 9.5 评估 → 9.6 LangChain 实践 建议工具：Python 3.10+ / LangChain / FAISS / 任意 LLM（在线 API 或本地 Ollama、vLLM 均可）
一、作业目标
不只要"跑通一个 RAG"，而是要
亲手拆开 RAG 的每一个模块，用实验数据说明每个模块到底有没有用、在什么情况下有用
。
完成本作业后，你应该能够：
独立搭建一条完整的 RAG 流水线（索引 → 检索前优化 → 检索 → 检索后优化 → 生成 → 编排）；
理解分块策略、检索策略（稀疏/稠密/混合）、重排序对最终答案质量的影响，并能用量化指标解释；
依据课件 9.5 节自建小型评测集，对检索模块与生成模块分别评估；
识别并分析 RAG 系统中的幻觉与失败案例，提出可落地的改进方案。

T3 检索前优化：查询分解与融合（对应课件 9.6 p39–40、9.2.2 p15）
原始查询往往表述模糊或包含多个子意图。本任务实现并对比以下策略：
查询改写（Query Rewrite）
：用 LLM 将口语化问题改写为检索友好形式；
多查询（Multi-Query）
：由一个原始问题生成 3–5 个语义等价/互补的查询，并行检索；
子查询 / 查询分解（Sub-Query）
：将复合问题拆成若干子问题（对应课件 9.6 的"查询分解"），分别检索子答案后综合；
结果融合（Fusion）
：对多路检索结果用 
倒数排名融合 RRF
 合并（对应课件 9.6 的"结果融合"）。
要求：
至少实现其中 
3 种
策略，在评测集上对比 Recall@5 与答案质量；
RRF 权重实验
：对 
score = α·dense + (1-α)·bm25
 之类的融合方式扫描 α ∈ {0, 0.3, 0.5, 0.7, 1}，画曲线说明最佳配比；
举一个 L2/L3 层级问题，展示"原始查询检索失败 → 分解/改写后检索成功"的完整过程（打印中间查询与召回片段）。
交付
：策略对比表 + RRF 权重曲线 + 单个案例的深度剖析。

稀疏检索
：BM25（TF-IDF 亦可，但需说明选择理由）；
稠密检索
：Embedding + 向量库（FAISS / Chroma 等）；
混合检索
：两者融合（RRF 或加权）。
要求：
计算三种检索器在 k ∈ {1, 3, 5, 10} 下的 
Recall@k
 与 
MRR@10
（课件 9.5.4，p36），画对比图；
构造 
至少 5 条"稠密检索赢"的查询
（语义相近但字面不重叠，如口语问法 vs 文档术语）和 
至少 5 条"稀疏检索赢"的查询
（含专有名词、编号、型号、低频术语），逐条列出两种检索器的 top-3 召回结果并分析原因；
明确指出：在你的语料上，混合检索是否真的带来了提升？如果没有，说明原因。

T5 检索后优化：重排序与压缩（对应课件 9.2.4，p17）
在 T4 的最优检索器之上，加入检索后处理：
重排序（Rerank）
：实现至少两种——① 基于规则的重排序（如按元数据、文档来源、时间加权）；② 基于模型的重排序（Cross-Encoder，如 
bge-reranker-base
，或按课件 9.4.4 的 JudgeRank 思路用 LLM 做 0-shot 点式打分：问题分析 → 文档摘要 → 相关性判断）。
对比"top-5 召回后重排取 top-3"与"直接取 top-3"的答案质量差异；
内容压缩（Compression）
：用小型语言模型或基于自信息量的方法对召回片段做压缩，只保留与问题相关的句子；
记录压缩前后的 
Context token 数
与答案质量，讨论"省下的 token 是否值得"；
分析重排序引入的
额外延迟
，给出延迟—质量权衡曲线。
交付
：重排/压缩前后对比表 + token 与延迟数据 + 权衡讨论。
T6 编排与设计模式（选做，对应课件 9.2.6 p19、9.3 p21–24）
在流水线中加入编排逻辑，至少实现以下之一：
路由（Routing）
：按问题类型路由到不同检索源或不同提示模板（规则判断 / 元数据路由 / LLM 判断 / 语义路由，任选）；
条件或分支模式
：预检索分支（按 L1–L4 等级走不同链路）或后检索分支；
循环模式
：加入判断模块（Judge Module），当"检索结果不相关 / 答案不确定"时自动改写查询重新检索，最多迭代 N 次（迭代型或自适应型）。
要求：画出你实现的 
RAG 流图
（节点 + 控制逻辑），并统计"触发二次检索的比例"及二次检索后的质量提升。
交付
：流程图 + 触发统计 + 效果对比。
T7 系统评估（必做其一：完整评估报告）（对应课件 9.5，p33–36）
对最终系统做一次系统评估，报告需覆盖：
检索模块指标
：MRR、MAP、Recall@k、Precision@k（课件 9.5.4）；
生成模块指标
：
忠实度（Faithfulness）：答案中的每个事实陈述是否都能在被召回的片段中找到依据 —— 逐条人工或 LLM 打分（1–5 分）；
正确性（Correctness）：与 
gold_answer
 对比，可用 EM / ROUGE-L / LLM-as-Judge；
幻觉率：无依据陈述数 / 总陈述数；
分层结果
：按 L1–L4 四类分别统计指标，画出柱状图，指出系统在哪一级任务上崩得最厉害；
失败案例归因
：对表现最差的 5 条，逐条标注失败环节是「检索失败 / 排序失败 / 生成失败 / 评测集本身有歧义」，并给出改进方案（对应课件 9.1.3 的三类难点：检索质量、系统效率、多模态扩展性）。
交付

八、常见问题
Q：没有 GPU / 没有 API Key 怎么办？
 A：可以用 Ollama 跑本地开源模型（如 
qwen2.5:7b
），embedding 用 
bge-small-zh-v1.5
，重排可用 
bge-reranker-base
 的 CPU 版本。检索部分（BM25 / FAISS）在 CPU 上完全够用，本作业的核心结论不依赖大模型规模。
Q：Recall@k 里的 "k" 到底怎么算？
 A：
gold_chunk_ids
 中至少有一个出现在 top-k 召回结果里，该条算命中。Recall@k = 命中条数 / 总条数。MRR 用 gold chunk 首次出现位置的倒数取平均（未命中的记 0）。
Q：评测集只有 20 条，结论可信吗？
 A：20 条是下限，鼓励做到 40–60 条。样本少时不要在报告里写"显著提升"这类强结论，应如实说明样本量限制——诚实地讨论局限性比编造显著性更得分。
Q：能不能用 LlamaIndex / 其他框架？
 A：可以，但框架只是工具。评分看的是你对模块的理解与实验设计，不是框架调用熟练度。若使用 LangChain 之外的框架，请在报告中说明各模块的对应关系。
